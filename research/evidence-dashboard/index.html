Personal R&D · Agentic Quality Engineering

An agent that writes, runs, and triages its own API tests — and holds up under audit.

Point it at a plain-English requirement. It writes an executable API test, runs it three times against a real app, and — on failure — a second agent triages the result blind. Only real bugs get reported, each with a five-step repro. Every number below is a measurement against a known-answer key, not a claim.

Code & harness → 60-sec live demo → Full evidence doc →

Run live against the Cypress Real World App (a full-stack banking demo) with Claude Sonnet 4.5. Nothing mocked.

01The loop

Each stage exists to remove one class of false positive. The agent (LLM) does judgement; deterministic code does selection, running, scoring, and every gating decision.

02Watch it work

One requirement — CYPRESS-RWA-TRANSACTIONS-007, "creates a new payment" — start to finish. From prose alone the agent wrote a test that re-fetches both balances and asserts the money moved, in cents. Nobody wrote that assertion.

Run 3× against the clean app pass, pass, pass Break the backend on purpose: - amount: transactionDetails.amount * 100, + amount: transactionDetails.amount, Same test, no changes fail, fail, fail Triage (blind) real_defect, high confidence, 5-step repro Revert the one line pass, pass, pass

The app, not the test, was the variable the whole time.

04The 18.2% that wasn't

The breadth run's raw false-positive rate looked like 18.2%. Instead of tuning it down, every failure was adjudicated by hand.

Real defects caught in the banking app — reclassified out of "false positive":
  • API 500-crashes when a password is omitted (should be a clean 4xx)
  • GraphQL createBankAccount mutation runs with no authentication
  • empty account numbers & invalid emails accepted without validation
  • a crash on a contacts lookup

Human adjudication on one app; ≈2–3% is a bounded estimate, not a constant. The "accuracy problem" was, in large part, the system doing exactly its job against a backend with weak validation.

05The hypothesis I killed

The obvious fix for false positives: give the agent a code knowledge graph — a dependency/side-effect map of the backend. I built it and ran a controlled A/B.

It did not reduce false positives; coverage even slipped by one. Why, from first principles: a test checks behaviour against an expected behaviour — the oracle. The oracle is a statement of intent, and intent is not present in the implementation. Deriving "what it should do" from the code under test is circular. No amount of code knowledge can supply a missing oracle. The real lever is the fidelity of the requirement itself.

Measured, not assumed — and killed cheaply rather than shipped on faith. Full A/B in the graphify decision memo.

06The standing red gate

Run end-to-end, the project's own acceptance gate (verify.sh) is red — it fails at the defect-catch step on that same structurally-unfixable pagination miss. Found while preparing this package, run twice to confirm it wasn't a flaky LLM call.

It's reported here rather than special-cased green. A green gate that lies makes every future green meaningless. Fixing it for real means earning a genuine catch or deliberately reclassifying that defect as an accepted gap — both real work, not a checkbox to tick.

07What this proves — and what it doesn't

Proven, live

Prose → runnable, meaningful API tests without seeing test code. Real bugs told apart from bad tests and noise (100% on a 12-case battery). Flake-guard and negative controls exercised live, not just unit-tested.

Out of scope

UI/E2E generation (API-level by design). A second, structurally different app (the core/adapter split is built for it; one wired up). A fully green standing gate. Rare, intermittent flakiness beyond a 3-run guard.

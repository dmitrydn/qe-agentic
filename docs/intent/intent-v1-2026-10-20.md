# QES Agentic Assets — Intent

**Owner:** Dmitry (QE Manager) · **Date:** 2026-10-20 · **Status:** intent agreed, not yet built
**Phase covered:** Phase 1 — first set of 5 QES agents, proven in an internal demo

---

## 1. Intent in one paragraph

Build five **independent QES agents** that check delivery work against the requirement. Each agent runs on its own as an engine, or as one step in a CI pipeline. Together they cover the points where BATC's delivery flow needs an independent check: requirement quality, test plan, claim vs reality, execution evidence and drift, and release readiness. The agents are **stack-agnostic, requirement-source-agnostic and LLM-provider-agnostic**, through adapters. They produce **evidence and recommendations; a person signs**. Phase 1 ends with an **internal demo on two open-source apps** (one Java, one TypeScript). Each agent's claims are backed by **pre-registered evals with confidence intervals**. After the demo, Dmitry and the BATC team jointly decide whether to fund Phase 2: the BATC adapter and a client pilot.

## 2. Why — the evidence this builds on

| Source | What it established | Implication for this project |
|---|---|---|
| Sandbox Stages 1–10 (`research/`) | The generate → run 3× → triage → score loop works live against a real app, with an app-agnostic core enforced by an import-boundary rule | Reuse the core; the mechanism is proven, not the accuracy |
| Stage 8–9 (Graphify NO-GO, requirements-first-principles) | The binding constraint is **requirement/oracle fidelity**, not code knowledge. The oracle is intent, and intent is not in the code | Requirement quality is the anchor (Agent 1) |
| Adversarial review A–E | Headline accuracy numbers were small-n, builder-labelled and partly tuned post hoc; "0% vs 18%" and the grounding win are not statistically significant; Stage 10 (pre-registered) was negative on false positives | Phase 1 must use pre-registered evals, independent labels and 95% CIs |
| BATC assessment (Oct 2026, `agentic-sdlc/batc-accelerator-assessment/`) | BATC's SDLC flow is sound; its QA skills fail on Java/Playwright; it has no behavioural evals; Bug 2347 is open; its claim-vs-evidence review is the most reusable pattern | Plug **into** BATC's flow; don't build **on** BATC's skills |
| BATC roadmap: Layer-4 plugin concept | Plugins may add skills, MCP tools and scoped instructions, and can never weaken governance (design intent, not built) | This is the natural home for the Phase 2 BATC adapter |

## 3. Scope — the five agents (Phase 1)

| # | Agent | BATC flow step | Input | Output | LLM vs deterministic |
|---|---|---|---|---|---|
| A1 | **Requirement quality check** | 1 Requirement, 2 Acceptance criteria | Requirement + ACs (via source adapter); optionally the app's interface (routes/contract) for grounding | Testability verdict per requirement, dimension ratings, clarification questions, assumptions log | LLM rates dimensions; code computes score, verdict and gating (sandbox testability-gate design) |
| A2 | **Test plan from the ACs** | 2 Acceptance criteria | Approved requirement + ACs + stack profile | Test plan (cases per AC, negative paths for risky ACs, traceability rows). **On request:** native test code for the target stack | LLM drafts; code enforces AC→case coverage and schema |
| A3 | **Claim-vs-reality review** | 5 Gap review | Requirement, claimed status, tests, execution evidence (from A4) | Gap list: AC covered and passing / covered, not run / partially asserted / not covered; over-claims; residual gaps with severity | Deterministic joins first; LLM only for assertion-strength judgement, labelled as triage |
| A4 | **Execution evidence + drift check** | 6 PR gate | Test results (JUnit XML, Playwright JSON), requirement versions, test↔requirement map | Evidence record per AC (what ran, when, result); drift report (requirement changed since tests were written; orphan or stale tests) | **Fully deterministic**, no LLM |
| A5 | **Release readiness from results** | 7 Release | A1–A4 outputs for the release scope | Readiness report: per-requirement status, open risks, recommendation, evidence links | Deterministic aggregation; LLM writes the summary only; recommendation is never a block |

**Independence rule:** every agent has its own input/output contract (JSON schema), its own CLI entry point and its own eval suite. It runs with or without the others. Composition happens in pipeline templates, not inside agents.

## 5. What "proven" means — Phase 1 exit criteria

All thresholds below are **proposals**. They are frozen in each agent's `evals/<agent>/preregistration.md` before the first measured run. Every result is reported with n and a 95% Wilson interval.

| Agent | Eval set (ground truth) | Proposed bar |
|---|---|---|
| A1 | ≥ 40 requirements per app: clean ones + seeded fidelity defects (missing oracle, ambiguous AC, phantom endpoint, unenforced constraint, epic-sized scope); second-model labels | Seeded-defect detection ≥ 80%; clean requirements wrongly flagged ≤ 15% |
| A2 plan | Same requirements, after A1 | 100% of ACs mapped to ≥ 1 case (deterministic); negative path present for every security/validation AC |
| A2 tests | Native tests on both apps + the seeded app-defect catalog (incl. negative controls) | Compile/run green on the clean app ≥ 85% of tests; seeded-defect catch rate reported with CI; negative controls not caught |
| A3 | Fixtures with seeded over-claims ("Tested" with no run, uncovered AC, half-asserted AC) | Over-claim detection ≥ 90%; false alarms ≤ 10% |
| A4 | Result files and requirement-change fixtures | 100% correct on fixtures (deterministic) |
| A5 | End-to-end release scenarios with known readiness | Report reproducible from inputs; recommendation agrees with label ≥ 90%; never blocks |
| Cross-cutting | All agents | Run on both apps with **no core change** (adapters/config only); import-boundary rule green; LLM provider switchable by config |

**Known weakness of the labelling choice:** a second AI model can share the builder model's blind spots. Seeded defects give model-free ground truth wherever possible, and a sample of second-model labels (≥ 20%) is spot-checked by a person before the demo.

## 6. Out of scope for Phase 1

- Client projects, client data or client LLM tenants
- BATC adapter implementation (contract design only)
- Azure DevOps / Jira / Confluence requirement adapters (the files adapter only)
- IDE skills front end
- Regression/triage agents, AI evaluation pack, pod model, effort baselines, proposal kit
- Performance, mobile, codeless and security-testing guild assets
- Any metric based on adoption, perceived productivity or code volume

## 8. Assumptions (correct me if wrong)

1. **Java demo app:** an open-source Spring app with a REST API and a web UI (candidate: Spring PetClinic, REST variant). To be confirmed at setup.
2. **Dev LLM:** OpenRouter (or direct API) is acceptable **inside the sandbox only**. Client providers arrive as adapters in Phase 2.
3. **Requirements format for the demo:** Markdown user stories with GIVEN-WHEN-THEN ACs, plus Gherkin `.feature` files, both through the files adapter.
4. **Pipeline templates:** Azure DevOps YAML first (matches BATC and delivery), GitHub Actions second.
5. **Sandbox code** (`agentic-qe-sandbox`) is reused by promoting tested modules into the new core, not by editing the research copy.
6. **Seeded defects** reuse the existing fault-injector approach on Cypress RWA; an equivalent catalog is built for the Java app.
